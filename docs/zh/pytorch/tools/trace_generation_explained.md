# Trace 文件是怎样生成的：从训练过程到运行记录

本文面向没有模型训练、性能分析经验的读者，预计阅读时间约 **10 分钟**。阅读后，你可以理解：trace 记录了什么、项目在哪里开始采集、为什么只记录某几步、文件由谁生成，以及拿到文件后应该先看什么。

本文以当前仓库默认的 `012` 运行实现为主，覆盖 MCore 和 FSDP2 两种训练后端。文末给出源码入口，方便需要进一步研究的读者查证。

## 1. 先认识 trace：给训练过程记一本带时间的流水账

可以把模型训练想象成一间多人协作的工厂：CPU 负责组织工作，NPU 负责大量计算，不同设备之间还需要交换结果。只看训练日志里的“这一轮用了 2 秒”，就像只知道工厂一天完成多少订单，无法知道时间花在了哪个环节。

**性能 trace 就是这间工厂的运行流水账。** 它把采集窗口内的活动写成事件，例如“某个矩阵计算何时开始、持续多久”“某次设备间通信何时执行”。分析工具把这些事件画成时间线，我们就能观察计算是否连续、通信是否与计算重叠，以及哪些地方出现空档。

项目里还有一种名称中带 trace 的功能：**模型输入输出采集**。它关注每个模型模块收到什么数据、输出什么数据、反向传播时梯度是什么情况。两者的用途如下：

| 你想回答的问题 | 对应功能 | 主要结果 |
| --- | --- | --- |
| 为什么训练慢？计算和通信各发生在什么时候？ | 性能采集，开关为 `profile` | 性能结果目录，其中可能包含 `trace_view.json` |
| 为什么训练结果异常？数据或梯度是否有问题？ | 模型输入输出采集，开关为 `model_io_trace` | 文本、JSONL 记录，以及按需保存的 `.pt` 张量文件 |

本文先沿着性能 trace 的生成过程讲解，再介绍模型输入输出 trace。它们是两套独立开关，开启其中一套不会自动开启另一套。

## 2. 理解流程需要的五个词

**训练步（step）**：模型读取一批训练数据、进行计算、根据误差调整参数的一次完整迭代。一次迭代可能拆成多个小批次，通常称为 micro-batch；所以一个 step 中出现多次模型调用是正常现象。

**rank**：分布式训练中给工作进程分配的编号。可以理解为“参与训练的第几位工人”。典型情况下一个进程负责一张设备卡，但 rank 是全局进程编号，不一定等于机器上的物理卡号。

**算子（operator）**：计算中的一个具体操作，例如矩阵乘法、加法。在设备侧，执行记录还可能细分为 kernel，也就是实际运行的计算任务；一段上层调用未必只对应一个设备任务。

**Profiler**：采集器，负责观察运行活动、记录时间和附加信息。本项目主要调用昇腾适配的 `torch_npu.profiler`。

**采集窗口**：真正保留运行记录的那几步。训练可以运行几千步，trace 只记录其中一两步，便于控制体积，也方便集中分析。

## 3. 从启动参数到文件，完整链路是什么？

可以按下面这条路线理解：

```text
用户配置采集开关、rank、步数、输出目录
                    ↓
项目检查：当前进程是否需要采集？
                    ↓
创建 Profiler：设定记录内容、采集日程、结果处理回调
                    ↓
训练开始前 start()：启动采集日程
                    ↓
训练逐步执行，每完成一轮调用 step() 推进日程
                    ↓
经过跳过、预热，进入正式记录窗口
                    ↓
窗口完成或停止时，由 Profiler 处理已采集的数据
                    ↓
回调触发解析，在配置目录下生成性能分析结果
                    ↓
用分析工具打开结果，查看时间线、算子、内存等信息
```

这里最重要的一点是：**项目负责决定“采什么、什么时候采、放在哪里”，底层 Profiler 负责采集、解析和导出性能文件。**

因此，在项目里找不到一段逐行拼接 `trace_view.json` 的代码是正常的。训练代码注册了 `tensorboard_trace_handler(输出目录)` 作为结果处理回调，真正的性能文件格式和解析细节由安装的 TorchNPU/CANN 工具链承担。

这个函数名虽然包含 TensorBoard，但在本项目中，它的直接作用是指定结果目录并提供采集结果处理入口；配置它不等于启动一个可视化网页。

### 3.1 第一道筛选：当前进程需要记录吗？

MCore 在 `training.py` 的 `is_profile_enabled()` 中判断：首先要打开 `--profile`，然后当前进程的 rank 要在 `--profile-ranks` 列表中。该实现用完整列表 `[-1]` 表示采集所有 rank。

FSDP2 把相同目的的判断放在 `ProfilerConfig.is_profiling_rank()` 中。关闭功能或未命中的进程不会创建实际采集器；它用列表中包含 `-1` 表示全部 rank。

这一步能明显减少结果数量。例如 8 个进程共同训练，只选 rank 0，就只采集这个进程对应的活动。代价是不能据此判断其他 7 个进程是否存在同样的问题。

### 3.2 第二道配置：要观察哪些活动？

两种后端创建 Profiler 时都默认选择 **NPU 活动**。开启 `profile_with_cpu` 后，才把 **CPU 活动**也加入采集范围。

同时观察 CPU 和 NPU 很有用：CPU 发出计算请求，与 NPU 真正执行计算，并不总是同一时刻发生。它们之间可能存在排队或等待。只看一侧，容易漏掉另一侧的原因。

项目还会把几个选项交给底层采集器：

| 选项 | 通俗解释 |
| --- | --- |
| `profile_level` | 选择底层采集级别，支持 `level_none`、`level0`、`level1`、`level2`；具体事件范围取决于工具链版本 |
| `profile_with_stack` | 记录调用路径，帮助把事件追溯到代码 |
| `profile_record_shapes` | 记录参与计算的数据尺寸，例如一个数字数组有多少行、多少列 |
| `profile_with_memory` | 请求记录内存相关信息，帮助分析内存使用 |
| `profile_export_type` | 选择 `text` 或 `db` 导出模式 |
| `profile_data_simplification` | 向底层传递结果精简选项 |

`level_none` 是传给底层的采集级别，不能直接当作项目总开关；项目是否创建采集器，主要由 `profile` 和 rank 筛选决定。额外信息越多，通常采集开销和文件体积也越大。

另外，`text` 是底层导出模式名称，不代表只会生成一个 `.txt` 文件。想获得 JSON 时间线时，应优先使用本文示例中的 `text` 模式，再以实际输出为准。

### 3.3 第三道配置：把训练背景一起写进去

项目会调用 `add_metadata_json()` 添加分布式训练背景。MCore 写入 rank、总进程数，以及张量并行、流水线并行、数据并行等配置；FSDP2 写入 rank 和总进程数。

这些信息像流水账封面上的“工厂规模、班组配置”，帮助分析者理解记录来自怎样的训练任务。它们属于背景信息，不是某个算子的开始时间或耗时。

## 4. 为什么调用了 start()，却没有马上记录？

因为 `start()` 启动的是**采集日程**。本项目通过 `schedule()` 告诉 Profiler 怎样经过下面几个阶段：

1. **跳过（skip_first）**：前几步暂时不采集。
2. **预热（warmup）**：让采集器做好准备，这部分不作为正式分析窗口保存。
3. **正式记录（active）**：保留这几步的运行活动。
4. **窗口完成**：处理采集结果。本项目设置 `repeat=1`，只安排一次窗口。

每轮训练结束后调用 `prof.step()`，作用相当于告诉采集器：“这一轮结束了，请进入下一轮。”它推进的是采集日程，不负责执行模型训练。

### 4.1 MCore：考虑已经完成了多少轮训练

MCore 的日程由 `get_profiler()` 构造。设定开始值为 S、结束值为 E，加载检查点后已经完成的迭代数为 I，代码计算：

```text
正式采集步数 active = E - S
跳过步数 skip_first = S - I - 2
如果 S == I + 1，预热步数为 0
如果 S >  I + 1，预热步数为 1
如果 S <= I，直接报错
```

例如全新训练时 I 为 0，设置 S 为 5、E 为 6：先跳过 3 轮，再预热 1 轮，随后正式记录 1 轮，也就是按“第 1 轮、第 2 轮……”数的**第 5 轮**。

若从已经完成 100 轮的检查点恢复，就需要选择 100 之后的采集开始值。代码会把已完成的 100 轮扣除，不能继续沿用开始值 5。

还要留意当前实现的边界：它直接使用 `E-S`，没有把结束值 `-1` 转成“直到训练结束”；开始值又被校验为必须大于 0。开始值恰好为 `I+1` 时，`skip_first` 计算结果是 `-1`，底层如何处理还取决于 TorchNPU 版本。实际使用时，优先选择未来几轮后的开始值和一个明确、大于开始值的结束值，例如 5 和 6。

### 4.2 FSDP2：从本次采集器启动时开始计数

FSDP2 的 `ProfilerManager` 使用另一套计算：

```text
结束值不是 -1 时：active = E - S
结束值是 -1 时：active = 1,000,000
skip_first = max(0, S - 1)
S 为 0 时，warmup = 0；否则 warmup = 1
```

全新训练时，S 为 5、E 为 6，意味着先跳过 4 轮、预热 1 轮，然后记录第 6 轮。若用从 0 开始的编号，这一轮就是 step 5。

**同样写 5 和 6，两种后端对应的实际训练轮次有区别。** MCore 示例是第 5 轮，FSDP2 示例是从 0 编号的 step 5，即第 6 轮。读配置时应结合所用后端。

FSDP2 还有一处恢复训练时的区别：代码虽然恢复了 `global_step`，但构造 Profiler 日程时没有扣除这个值，采集器内部又从头计数。因此，恢复训练后不能直接把这里的开始值当成恢复后的绝对 `global_step`。结束值 `-1` 的实现也实际对应一个很大的有限窗口，正常停止时再收尾。

## 5. 训练代码在什么位置启动、推进和结束采集？

MCore 的主要逻辑位于 `mindspeed_llm/training/training.py`：在训练循环前创建 Profiler 并调用 `start()`；在循环靠末尾的位置调用 `step()`；离开循环后调用 `stop()`。

所以采集窗口观察的是这段运行期间的活动，可能包含计算、通信，以及窗口内的其他被记录操作，不能把它简单理解为只包住一次模型前向计算。

FSDP2 把对象创建放在 Trainer 初始化阶段，把 `start()` 放在训练循环前。每次完成小批次累积、参数更新和步数递增后，调用 Profiler 的 `step()`；训练流程结束时调用 `stop()`。

两套实现都将下面这个回调交给底层：

```python
on_trace_ready = torch_npu.profiler.tensorboard_trace_handler(结果目录)
```

正式窗口完成时，底层根据日程触发结果处理；`stop()` 则负责结束当前采集状态并进行相应收尾。若训练提前终止、没有到达正式窗口，或者没有正常完成收尾，就可能得不到预期结果。

## 6. 实际怎样开启，并找到生成的文件？

下面都是**添加到现有、能够正常运行的训练配置中的片段**。完整训练还需要模型、数据、分布式环境等配置。运行脚本时应从项目根目录出发。

MCore 在已有训练启动命令后追加：

```bash
--profile \
--profile-step-start 5 \
--profile-step-end 6 \
--profile-ranks 0 \
--profile-level level1 \
--profile-with-cpu \
--profile-export-type text \
--profile-save-path ./profile_trace
```

FSDP2 在已有 YAML 的 `training` 字段中合入：

```yaml
training:
  profile: true
  profile_step_start: 5
  profile_step_end: 6
  profile_ranks: [0]
  profile_level: level1
  profile_with_cpu: true
  profile_export_type: text
  profile_save_path: ./profile_trace
```

选择较短窗口，可以先观察一次稳定训练迭代，避免启动阶段的初始化活动主导分析。若要研究启动阶段本身，则应专门选择对应窗口。

结果目录通常类似下面这样，具体名称及文件组合由工具链版本和导出选项决定：

```text
profile_trace/
└── 主机名_进程号_时间戳_ascend_pt/
    ├── ASCEND_PROFILER_OUTPUT/
    │   └── trace_view.json       # 常见的解析后时间线文件
    ├── logs/
    └── PROF_.../
        ├── device_0/data/       # 设备侧原始采集数据
        └── host/data/           # 主机侧原始采集数据
```

可以把 `PROF_...` 下的原始数据理解为“现场记录”，把解析输出理解为“整理后可供分析的报表”。配置的保存路径是结果根目录，通常需要再进入自动生成的子目录寻找时间线。多进程采集也不意味着会自动合并成一个总 JSON 文件。

## 7. trace_view.json 里的一条记录是什么意思？

时间线文件常用 `traceEvents` 列表保存事件。下面是为了说明字段而编写的简化示例，不是本次实际训练结果：

```json
{
  "traceEvents": [
    {
      "name": "MatMul",
      "cat": "kernel",
      "ph": "X",
      "ts": 1000,
      "dur": 250,
      "pid": 123,
      "tid": 7,
      "args": {"stream_id": 2}
    }
  ]
}
```

它表示一个名为 `MatMul` 的事件，在这份时间线使用的时间坐标 1000 处开始，持续 250 个时间单位。昇腾此类时间线通常使用微秒，因此这里的持续时间是 250 微秒，也就是 0.25 毫秒。

| 字段 | 可以怎样理解 |
| --- | --- |
| `name` | 做了什么，例如一个计算或通信操作 |
| `cat` | 事件类别，帮助工具分类显示 |
| `ph` | 事件采用什么表达形式；`X` 常表示带开始时间和持续时间的完整事件 |
| `ts`、`dur` | 何时开始、持续多久 |
| `pid`、`tid` | 时间线中用于组织事件的进程和线程标识；部分轨道可能是工具构造的逻辑标识 |
| `args` | 补充信息，可能包含设备流编号、关联编号等 |

并非每条事件都有 `dur`。有的记录用于标注线程名称，有的表示关联关系。也不能把所有事件耗时直接相加当作训练耗时：CPU 调用与设备执行可能对应同一项工作，不同设备流还可能并行运行。

拿到结果后，可以参考项目已有的[性能数据采集文档](profiling.md)，用 MindStudio Insight 查看时间线。先关注较长空档、长时间通信和重复出现的慢算子，再结合 CPU 调度与设备执行判断原因。单个事件很长只能说明它值得检查，不能直接证明它就是整体瓶颈。

## 8. 模型输入输出 trace：怎样把数据写进文件？

这条链路的核心是 `mindspeed_llm/tools/model_io_trace.py` 中的 `ModelIOTraceManager`。与性能采集不同，**这些文本、JSONL 和张量文件确实由项目自己的代码直接写出。**

它的工作过程是：

1. 创建管理器时读取配置，确定采集哪些 rank、哪些 step、哪些模块，以及使用什么输出格式。
2. 训练迭代开始时调用 `start_step(model, step)`，检查当前 rank 和 step 是否命中。
3. 命中后创建目录、打开文件，并在模型上安装 hook。
4. 模型运行时，hook 自动收集输入、输出和梯度；模型入口处的 hook 额外提取训练数据字段预览。
5. 迭代结束时调用 `end_step()`，移除 hook、关闭文件。

hook 可以理解为安装在工序入口和出口的临时观察点。前向 hook 记录模型模块这次计算的输入和输出；完整反向 hook 记录输入侧、输出侧梯度，**并不等于逐个保存模型参数的梯度**。

默认配置只采集 rank 0、step 0，主要关注没有子模块的“叶子模块”，同时跳过 Identity 一类直接透传模块和概率接近 0 的 Dropout。可以用模块名称匹配规则缩小范围。

两种后端的模型输入输出采集都在步数递增前传入当前迭代编号，因此全新训练的第一次迭代是 step 0。配置 `steps: ["3-5"]` 会包含 3、4、5 三步；`steps: ["all"]` 表示全部步骤。这里的范围规则与性能采集的“结束值不包含在内”不同。

### 8.1 输出文件各自有什么用？

```text
model_io_trace_output_path/
└── rank0/
    └── step0/
        ├── output.txt          # text 或 both 模式
        ├── token_ids.log       # text 或 both 模式
        ├── module_io.jsonl     # jsonl 或 both 模式
        ├── batch_inputs.jsonl  # jsonl 或 both 模式
        └── tensors/            # tensor 模式且实际保存了张量时
            └── 00000000_...pt
```

`output.txt` 便于人工阅读模块输入输出。`token_ids.log` 保存模型入口处可找到的字段预览，例如 token 编号、标签和位置编号；token 编号是数字，不会自动还原成自然语言。

JSONL 表示“一行一个 JSON 对象”。`module_io.jsonl` 通常一行对应一个张量，记录模块名、前向或反向阶段、数据尺寸、类型、设备和统计量。`batch_inputs.jsonl` 保存入口字段预览，找不到的字段进入 `missing_fields`，不代表数据一定丢失，也可能是当前模型入口没有这个参数。

一次 step 中有多个 micro-batch、重复调用或重计算时，同一模块会出现多次记录。JSONL 的 `sequence` 只是对应文件内从 0 开始的记录序号；这套记录没有提供性能时间线所需的开始时间和持续时间。

### 8.2 三个容易读错的细节

第一，统计量基于**绝对值**。例如原数据是 `[-2, 1]`，计算用的是 `[2, 1]`，所以最大值为 2、最小值为 1。文本里的 `sum` 也不是原始正负数的直接求和。

第二，默认的 `output_format` 是 `text`。即使 `tensor.mode` 是 `statistics`，文本路径仍会把张量转到 CPU 的 float32 类型，打印数值表示并计算四项绝对值统计；较大的张量可能按 PyTorch 的打印规则省略部分内容。需要完整数值文件时，要使用 `tensor.mode: "tensor"`，保存为 `.pt`。JSONL 路径才按配置的 `tensor.statistics` 列表选择统计项。

第三，batch 只做截断预览，默认最多 2 行、每行 64 个元素。高维数据先按最后一维整理成行再截取。因此预览适合快速核对输入，不能当作整个训练批次的完整备份。

具体开启方式和完整配置见[模型输入输出采集文档](model_io_trace.md)。这条路径会增加统计、设备到 CPU 的数据传输和磁盘写入开销；如果与性能采集同时开启，性能 trace 也可能观察到这些额外工作。

## 9. 文件生成之后，Chakra 脚本做什么？

当前工作区的 `mindspeed_llm/tools/chakra_trace.py` 是一个读取已有时间线的辅助脚本。直接从项目根目录运行：

```bash
python mindspeed_llm/tools/chakra_trace.py \
  --input ./profile_trace/具体结果目录/ASCEND_PROFILER_OUTPUT/trace_view.json
```

它读取并检查 `traceEvents`，根据名称和类别中的标记将事件粗分为计算、通信和其他事件，保留时间、设备流和关联信息，再按共享关联编号、flow 标识、同进程同设备流等规则连接相邻事件，最后向终端打印 JSON 统计。

它属于**采集之后的读取与初步分析环节**，当前命令不会启动训练，也不会输出 Chakra 格式的执行轨迹。按名称、类别和关联键建立的关系仍需要结合实际数据核对；例如跨设备流仅凭时间先后，无法说明谁依赖谁。

## 10. 没找到预期文件时，按生成链路排查

| 现象 | 先检查什么 | 原因 |
| --- | --- | --- |
| 输出目录没有预期结果 | 功能开关、当前 rank、输出路径 | 未开启或 rank 未命中时，可能根本没有创建采集器 |
| 有结果，但没有目标训练步骤 | 开始值、结束值、后端和恢复位置 | 两套性能日程计数方式不同，训练也可能在窗口前结束 |
| 有原始数据，暂时没有时间线 JSON | 解析日志、导出模式、工具链版本、是否完成收尾 | 采集原始数据和解析为时间线是不同阶段 |
| 看得到 NPU，找不到预期 CPU 活动 | `profile_with_cpu` | 默认采集活动只包含 NPU |
| `output.txt` 有内容，却没有 `trace_view.json` | 开启的是哪一套 trace 功能 | 模型输入输出采集生成数据记录，性能采集生成时间线结果 |
| 输入输出结果没有 `.pt` | `tensor.mode` 以及是否有张量被捕获 | 默认统计模式不会保存完整张量文件 |
